# 投递记录第一版设计稿

## 背景

当前插件已经具备较完整的网申资料维护与填写能力，包括 `快速填充`、`AI 扫描填充`、`AI 框选补填`、信息浮窗逐字段写入、简历解析、本地备份与 WebDAV 同步。但这些能力主要服务于“如何填表”，缺少一层围绕“我投了什么、现在进展到哪里”的投递跟踪能力。

参考项目 `jobtracker` 已验证了“从职位页读取基础信息并在本地管理投递记录”的价值，但当前插件已有更成熟的资料与设置体系，因此第一版投递记录不应做成脱离现有设置体系的独立工具，而应嵌入当前插件工作流，成为手动触发、轻量管理的一项新增能力。

## 目标

- 增加一套由用户手动触发的 `投递记录` 能力。
- 在 popup 右上角提供 `新建投递记录` 与 `查看投递记录` 两个入口。
- `新建投递记录` 时尽量自动预填基础字段，但不自动提取 `岗位名`。
- 在设置页新增 `投递记录` 标签，并放在 `数据与同步` 后面。
- 第一版支持公司名搜索筛选、岗位名搜索筛选、状态筛选、字段编辑、状态修改和来源链接打开。
- 投递记录内部使用结构化数据存储，单独支持 CSV 导入导出。

## 非目标

- 不自动监听网页提交成功并自动落库投递记录。
- 不自动提取 `岗位名`。
- 不在第一版中提供统计面板、趋势图、批量操作或多维报表。
- 不在第一版中将投递记录并入现有“完整 JSON 备份”的主链路。
- 不在第一版中改造 WebDAV 同步语义，使其专门支持投递记录 CSV 文件。

## 核心原则

### 手动触发

投递记录只在用户明确点击 `新建投递记录` 时创建，不根据浏览职位页、打开 popup、执行填充动作或页面提交结果自动写入。

### 自动预填但不过度猜测

第一版只自动预填识别稳定且风险较低的字段，如 `公司名`、`来源站点`、`来源链接`、时间。`岗位名` 不自动提取，避免把页面标题、栏目标题或其他噪声信息误识别为岗位。

### 管理入口复用现有设置页

记录管理不新增独立主页面，统一进入现有设置页的新标签，减少导航分散，并复用现有设置页的空间与样式体系。

### 数据模型与导入导出解耦

内部以结构化对象数组存储，确保后续筛选、编辑、状态更新和测试都保持清晰。CSV 仅作为用户可见的导入导出格式，不作为内部主存储格式。

## 用户体验

### popup 入口

popup 右上角新增一个纵向操作区，包含两个上下排列的按钮：

- `新建投递记录`
- `查看投递记录`

这两个按钮属于辅助操作，不与现有 `快速填充`、`AI 扫描填充`、`AI 框选补填` 主操作混排在同一主按钮区。

### 新建投递记录

用户点击 `新建投递记录` 后，插件打开一个轻量确认表单。该表单应尽量预填以下内容：

- `公司名`
- `来源站点`
- `来源链接`
- `投递时间`
- `创建时间`

其中：

- `岗位名` 保留为可编辑字段，但默认不自动提取；
- `状态` 默认值为 `已投递`；
- 用户可在保存前补充或修改任意字段；
- 保存前若命中重复记录，显示轻提醒 `已存在`，但仍允许继续新建。

### 查看投递记录

用户点击 `查看投递记录` 后，插件打开设置页，并直接切换到新增的 `投递记录` 标签。该标签位于 `数据与同步` 后面。

第一版记录页支持：

- 按公司名搜索与筛选；
- 按岗位名搜索与筛选；
- 按状态筛选；
- 修改状态；
- 编辑投递记录的各个字段；
- 点击来源链接后在浏览器中打开原页面；
- 单独 CSV 导入；
- 单独 CSV 导出。

## 范围

本设计涉及：

- `src/popup/App.tsx` 中 popup 入口区的新增按钮；
- 一个用于新建投递记录的轻量表单页或弹层；
- 设置页新增 `投递记录` 标签；
- 投递记录的数据模型、存储读写、筛选与编辑；
- 投递记录的 CSV 导入导出；
- 相关消息协议、背景页 handler 与测试。

本设计不涉及：

- 表单自动提交检测；
- AI 参与投递记录识别；
- 统计图表；
- 批量导入职位页面并自动批量建档；
- 现有用户资料、简历解析、AI 配置与 WebDAV 逻辑的结构性重构。

## 状态流

第一版固定支持以下状态：

- `待投`
- `已投递`
- `笔试`
- `面试`
- `Offer`
- `终止`

这些状态既可用于新建时选择，也可在记录列表中后续修改。第一版不支持用户自定义状态，也不支持状态颜色配置。

## 数据模型

建议新增 `ApplicationRecord` 结构，至少包含以下字段：

- `id`
- `companyName`
- `jobTitle`
- `sourceSite`
- `sourceUrl`
- `status`
- `notes`
- `appliedAt`
- `location`
- `createdAt`
- `updatedAt`

字段语义约束如下：

- `id`：本地唯一标识，用于编辑、删除、导出和测试。
- `companyName`：公司名称，允许自动预填，也允许用户修改。
- `jobTitle`：岗位名称，第一版不自动提取，默认可为空。
- `sourceSite`：来源站点，如当前域名或站点名称。
- `sourceUrl`：当前页面完整链接，用于回溯来源和重复判断。
- `status`：上述固定状态之一，新建默认 `已投递`。
- `notes`：自由备注。
- `appliedAt`：用户认定的投递时间。
- `location`：岗位地点，可选。
- `createdAt`：本地创建记录时间。
- `updatedAt`：最后一次编辑时间。

## 存储设计

投递记录应独立于 `UserProfile` 存储，不与当前个人资料对象混放。原因：

- 个人资料是“候选人静态信息”，投递记录是“职位级动态信息”；
- 混在同一对象下会让更新粒度、备份边界和测试职责变得模糊；
- 后续若投递记录数量增加，独立存储更利于单独读写与迁移。

建议新增独立存储键，例如：

- `applicationRecords`

内部值为 `ApplicationRecord[]`。

## 预填策略

### 自动预填字段

第一版推荐自动预填：

- `companyName`
- `sourceSite`
- `sourceUrl`
- `appliedAt`
- `createdAt`
- `updatedAt`

### 不自动预填字段

第一版明确不自动提取：

- `jobTitle`

原因：

- 不同站点职位标题结构差异大；
- 同一页面常同时出现职位名、栏目名、相关推荐和站点标题；
- 错填岗位名会明显损害记录质量，且修正成本高于少填。

### 公司名提取要求

公司名允许采用启发式提取，但必须接受识别不稳定这一现实，因此表单中必须允许用户修改。第一版不要求做到全站稳定识别，也不将识别失败视为整单失败条件。

## 重复判断

新建时执行轻量重复检查，命中条件为：

- `companyName` 相同；
- `sourceUrl` 相同。

若命中：

- 显示提示 `已存在`；
- 不阻止保存；
- 不自动跳转已有记录；
- 不自动合并。

该规则的目标是提醒误操作，而不是定义严格唯一键。第一版接受“同公司不同链接”和“同链接公司名被用户修正”的边界差异。

## 记录页设计

### 标签位置

设置页新增 `投递记录` 标签，并置于 `数据与同步` 后面。

### 列表能力

第一版列表页必须支持：

- 公司名搜索；
- 岗位名搜索；
- 状态筛选；
- 点击记录打开编辑界面；
- 在记录中点击来源链接打开原始页面。

### 编辑能力

第一版支持编辑投递记录的全部字段，而不仅限于状态和备注。建议采用“列表 + 编辑表单”的方式，而不是把所有字段直接塞入单行表格中做全量行内编辑。

原因：

- 字段较多，包含链接、备注和时间；
- 设置页已有较多内容，需要控制密度；
- 编辑表单更容易复用新建表单组件与校验逻辑。

## CSV 导入导出

### 原则

投递记录采用“单独 CSV 导入导出”方案，不与现有完整 JSON 备份互相替代。

### 第一版范围

第一版应支持：

- 从当前投递记录导出 CSV；
- 从用户选择的 CSV 文件导入投递记录；
- 在导入前做基本表头校验与字段解析。

### 推荐列头

建议固定以下 CSV 列头：

- `companyName`
- `jobTitle`
- `sourceSite`
- `sourceUrl`
- `status`
- `notes`
- `appliedAt`
- `location`
- `createdAt`
- `updatedAt`

第一版可以不要求导入文件包含 `id`。若缺少 `id`，导入时由本地重新生成。

### 导入策略

CSV 导入时：

- 逐行解析为结构化记录；
- 对缺失字段采用空值处理；
- 对非法状态值做失败提示或跳过处理；
- 生成新的本地 `id`；
- 对时间字段做尽量保守的解析，无法识别时保留原文本或空值。

第一版不要求导入时做复杂去重合并。若导入数据与本地已有记录重复，可沿用轻量策略：允许导入，必要时在导入结果摘要中提示可能存在重复。

## 架构建议

### popup

在 `src/popup/App.tsx` 中新增右上角操作区，并提供：

- 打开新建投递记录表单；
- 打开设置页并切换到 `投递记录` 标签。

### options

在 `src/options/App.tsx` 中新增一个独立 `投递记录` 标签，并建议把记录列表与编辑表单拆成独立组件，而不是继续堆在主文件里。

建议新增：

- `ApplicationRecordsSection`
- `ApplicationRecordEditor`

### shared

在 `src/shared/types.ts` 中新增：

- `ApplicationRecord`
- 相关消息类型与响应类型

在 `src/shared/storage.ts` 中新增：

- 读取投递记录列表；
- 保存全部投递记录；
- 新增单条记录；
- 更新单条记录；
- 删除单条记录；
- CSV 导入导出辅助方法或调度入口。

### background

在 `src/background/index.ts` 中新增投递记录相关消息处理，如：

- 获取列表；
- 新建记录；
- 更新记录；
- 删除记录；
- 导出 CSV；
- 导入 CSV 预检或导入执行。

这些 handler 应与当前用户资料、备份、同步逻辑并列，不应混入 `SAVE_USER_PROFILE` 等现有分支。

## 测试要求

至少覆盖以下场景：

- popup 中能看到 `新建投递记录` 与 `查看投递记录` 两个按钮。
- `查看投递记录` 能打开设置页并切到 `投递记录` 标签。
- `新建投递记录` 默认状态为 `已投递`。
- `岗位名` 第一版不做自动预填。
- 自动预填字段能被用户修改。
- 命中 `同公司 + 同链接` 时提示 `已存在`，但保存仍可继续。
- 公司名搜索、岗位名搜索和状态筛选能正确生效。
- 可编辑单条记录的全部字段。
- 点击来源链接可打开原始页面。
- CSV 导出列头稳定且内容完整。
- CSV 导入能正确解析合法文件，并对非法状态或异常表头做明确处理。

## 验收标准

- popup 右上角存在 `新建投递记录` 与 `查看投递记录` 两个按钮。
- 点击 `新建投递记录` 后，用户能看到带默认值的确认表单。
- 新建表单默认状态为 `已投递`。
- 新建表单会自动预填公司名、来源站点、来源链接和时间信息。
- 第一版不会自动提取岗位名。
- 点击 `查看投递记录` 后，设置页可进入新增的 `投递记录` 标签。
- 记录页支持公司名搜索、岗位名搜索、状态筛选。
- 记录页支持修改状态与编辑全部字段。
- 点击来源链接可打开原页面。
- 命中 `同公司 + 同链接` 时只提示 `已存在`，不阻止用户继续新建。
- 投递记录内部采用结构化存储。
- 投递记录支持单独 CSV 导入导出。

## 风险

- 公司名自动提取在不同招聘站点上的稳定性有限；
- 若把记录页直接堆在 `src/options/App.tsx`，后续可维护性会快速下降；
- CSV 导入在时间格式、换行备注和编码差异上容易出现边界问题；
- 后续若用户希望把投递记录也纳入完整同步链路，当前“单独 CSV 导入导出”方案还需要再次设计与现有 JSON 备份的关系。

## 结论

第一版投递记录应定位为“由用户手动触发的新建与管理能力”，而不是自动跟踪系统。它复用 popup 作为入口、复用设置页作为管理界面，避免过早引入自动识别与自动落库的复杂度。通过结构化存储 + 单独 CSV 导入导出，可以在尽量小的实现范围内把“新增记录、查找记录、更新状态、回看来源链接”这一最小闭环先跑通。
