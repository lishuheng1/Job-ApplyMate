# 投递记录表格视图设计稿

## 背景

投递记录功能已经完成基础管理能力，但当前展示方式仍不符合“批量查看和快速筛选”的使用习惯。当前实现主要存在这些问题：

- 列表不是标准表格形态，列信息不够明确；
- 链接列与操作按钮占用较多空间；
- 顶部单独筛选框与列表本体割裂；
- 点击编辑后仍要切换到额外的编辑容器，无法直接在表格内修改。

这一轮目标是把投递记录管理页收敛成更接近电子表格/后台列表的形态，让浏览、筛选、排序和编辑都围绕同一张表完成。

## 目标

- 投递记录展示区改成真正的表格视图。
- 每一列显示明确列名，如 `公司`、`岗位`、`链接`。
- 去掉顶部独立筛选框，把排序与筛选入口都收进列头。
- 点击某一行的 `编辑` 后，该行直接切换成可编辑态，在单元格中直接修改内容。
- `链接` 列在浏览态显示为普通文本，不再显示超链接，也不再保留单独的 `打开链接` 按钮。

## 非目标

- 不修改投递记录 schema。
- 不新增批量编辑、批量删除、固定列、拖拽列宽等复杂表格能力。
- 不引入第三方 data-grid 组件库。
- 不修改 CSV 导入导出逻辑。
- 不修改 popup 与新建页以外的其他页面结构。

## 用户体验

### 表格列

表格至少包含这些列：

- 公司
- 岗位
- 链接
- 状态
- 来源站点
- 投递日期
- 工作地点
- 备注
- 操作

列名直接显示在表头，不再依赖用户从行内容里自行推断字段语义。

### 链接列

浏览态下：

- 链接列显示为普通文本；
- 使用固定列宽；
- 内容超出列宽时隐藏并省略显示；
- 不渲染为可点击超链接。

编辑态下：

- 链接列直接变成文本输入框；
- 用户可像修改其他单元格一样直接修改链接值。

### 编辑方式

点击某一行的 `编辑` 图标后：

- 不再展开单独编辑表单；
- 不再显示右侧编辑卡片；
- 当前行整行切换成编辑态；
- 可编辑列在原位变成输入框或下拉框；
- 行尾操作切换为 `保存`、`取消`、`删除图标`。

任意时刻只允许一行进入编辑态，避免多个草稿同时存在。

### 排序与筛选

每个列头都带两个小控制：

- 排序符号
- 筛选符号

点击排序符号后：

- 按当前列进行升序/降序切换；
- 第一版仅支持单列排序。

点击筛选符号后：

- 在该列表头下方弹出一个小浮层输入框；
- 用户直接在这个浮层里输入筛选值；
- 当前列按文本包含关系过滤结果。

这意味着顶部独立筛选框将被移除。

本设计涉及：

- `src/options/ApplicationRecordsSection.tsx`

## 交互设计

### 排序

第一版排序范围建议覆盖全部可见列，但实现逻辑按字段类型分成两类：

- 文本列：按字符串比较
- 日期列：按 `appliedAt` 文本或可解析日期比较

每次只有一个激活的排序列与方向。

### 筛选浮层

筛选浮层应具备：

- 与对应表头绑定；
- 可输入单个文本值；
- 可清空当前列筛选；
- 点击浮层外区域时关闭。

为了保持实现简单，第一版不做多条件可视化标签，也不做高级运算符。

### 操作列

浏览态操作列：

- `编辑` 图标
- `删除` 图标

编辑态操作列：

- `保存`
- `取消`
- `删除` 图标

这里不再单独放置 `打开链接` 按钮，因为链接已成为普通字段展示的一部分。

## 视觉设计

### 表格

整体应采用标准数据表样式：

- 顶部为表头；
- 下方为多行数据；
- 行与行之间用细边框区分；
- hover 和选中编辑态需要有清晰但不过重的高亮。

### 列宽

链接列宽度固定，不随内容增长。  
长链接在浏览态下通过：

- `overflow: hidden`
- `text-overflow: ellipsis`
- `white-space: nowrap`

进行截断。

备注列也应控制宽度，避免把整行撑得过宽。

### 图标

继续沿用当前线性 SVG 图标风格：

- 编辑：铅笔
- 删除：垃圾桶
- 排序：上下箭头或方向符号
- 筛选：漏斗

不引入图标字体或外部图标库。

## 架构建议

### 视图状态

`ApplicationRecordsSection` 中建议新增两类 UI 状态：

- 排序状态：当前字段 + 方向
- 筛选状态：按字段记录输入值

原有 `editingId` 与 `draftRecord` 状态可以继续沿用，用于控制单行编辑。

### 渲染方式

建议直接使用原生表格语义渲染：

- `<table>`
- `<thead>`
- `<tbody>`
- `<tr>`
- `<th>`
- `<td>`

这样更符合“列头 + 行编辑”的结构，也便于后续继续扩展列级交互。

### 编辑态

编辑态与浏览态共用同一张表。  
具体某一行是否显示输入控件，完全由 `editingId === record.id` 决定，不另起单独编辑面板。

## 测试要求

至少覆盖以下场景：

- 表格列头渲染明确列名。
- 顶部独立筛选框已移除。
- 点击列头排序按钮后，列表顺序发生变化。
- 点击列头筛选按钮后，出现当前列的筛选输入浮层。
- 输入筛选值后，表格按该列文本过滤。
- 点击 `编辑` 图标后，该行直接进入编辑态。
- 编辑态下链接列渲染为普通文本输入框，而不是超链接。
- 编辑态下点击 `保存` 后，仍然发送原有更新消息。

## 验收标准

- 投递记录展示区为表格形式。
- 每列都有清晰列名，如 `公司`、`岗位`、`链接`。
- 顶部独立筛选框消失。
- 每列标题带排序与筛选入口。
- 筛选入口点击后，在列头下方弹出输入浮层。
- 链接列使用固定宽度，超长内容被截断隐藏。
- 浏览态下链接不是超链接。
- 点击编辑后，该行直接切换成可编辑态。
- 不再出现独立展开的编辑表单或右侧编辑卡片。

## 风险

- 直接切成表格后，窄屏下可能出现横向空间紧张，需要容器支持水平滚动。
- 列头浮层筛选如果处理不好层级和定位，容易被表格容器裁切。
- 单行编辑态字段较多，若列宽过窄，需要合理取舍哪些列在编辑态中保持输入框、哪些列允许缩窄。

## 结论

这一轮应把投递记录管理页正式收敛成数据表格，而不是“列表卡片的变体”。通过列头排序/筛选、固定宽度的链接列和整行编辑态，用户可以更自然地把这块区域当作“投递记录台账”来使用。
